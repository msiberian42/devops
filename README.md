## Домашнее задание к занятию 17 «Инцидент-менеджмент»

**Краткое описание инцидента**

21 октября 2018 года в результате сбоя сетевого соединения между сетевым узлом на восточном побережье США и основным центром обработки данных GitHub произошёл отказоустойчивый переход кластеров MySQL на западное побережье. Это привело к нарушению согласованности данных и существенному ухудшению работы платформы.

Инцидент продолжался 24 часа 11 минут. Пользователи сталкивались с медленной загрузкой страниц, отображением устаревших и противоречивых данных. Доставка веб-хуков и сборки GitHub Pages были приостановлены. Потери пользовательских данных не произошло.

**Предшествующие события**

21 октября в 22:52 UTC проводились плановые работы по замене неисправного оптического оборудования с пропускной способностью 100G. В результате этих работ на 43 секунды было потеряно сетевое соединение между сетевым узлом и основным центром обработки данных на восточном побережье США.

В этот момент система управления кластерами MySQL (Orchestrator) автоматически инициировала переключение основных серверов на западное побережье. После восстановления соединения приложения начали направлять операции записи на новые основные серверы, хотя в базах данных восточного побережья оставались операции записи, которые не успели реплицироваться.

**Причина инцидента**

Непосредственной причиной стало кратковременное разделение сети (network partition), вызванное плановыми работами по замене сетевого оборудования. Алгоритм консенсуса Raft позволил Orchestrator сформировать кворум на других площадках и автоматически переключить основные серверы баз данных на западное побережье.

Корневая проблема заключалась в несоответствии конфигурации Orchestrator возможностям приложений. Система могла переключать основные серверы между регионами, однако приложения не были рассчитаны на работу с дополнительными межрегиональными задержками. Кроме того, отсутствие репликации части операций записи привело к расхождению данных между двумя центрами обработки данных и невозможности безопасно вернуть исходную топологию.

**Воздействие**

Инцидент затронул несколько кластеров MySQL и привёл к следующим последствиям:
- Ухудшение производительности и доступности GitHub на протяжении 24 часов и 11 минут.
- Отображение пользователям устаревших и противоречивых данных из-за задержек репликации.
- Увеличение времени загрузки страниц и выполнения операций записи.
- Приостановка доставки веб-хуков и сборок GitHub Pages.
- Накопление в очередях более 5 миллионов событий веб-хуков и 80 тысяч сборок GitHub Pages.
Пользовательские данные не были потеряны. Однако около 200 тысяч событий веб-хуков были удалены из-за превышения внутреннего TTL. Несколько секунд операций записи, не попавших в репликацию, потребовали последующей ручной сверки.

**Обнаружение**

Инцидент был обнаружен внутренними системами мониторинга, которые в 22:54 UTC начали генерировать многочисленные оповещения о сбоях.

К 23:02 UTC инженеры первой линии реагирования установили, что топологии нескольких кластеров баз данных находятся в неожиданном состоянии. Запрос к API Orchestrator показал, что в топологии репликации присутствуют только серверы западного побережья США. В 23:09 UTC сайту был присвоен жёлтый статус, а в 23:13 UTC инцидент был эскалирован до красного уровня.

**Реакция**

Команда реагирования вручную заблокировала внутренние инструменты развёртывания, чтобы предотвратить дополнительные изменения инфраструктуры. К устранению проблемы были привлечены инженеры команды разработки и сопровождения баз данных.

Для предотвращения потери и повреждения пользовательских данных было принято решение приостановить доставку веб-хуков и сборки GitHub Pages. Приоритет был отдан целостности данных, а не доступности сервисов. Также было решено восстановить базы данных из резервных копий, синхронизировать реплики и вернуть исходную топологию.

**Восстановление**

Восстановление выполнялось путём загрузки резервных копий MySQL, синхронизации реплик между центрами обработки данных и последующего переключения основных серверов обратно на восточное побережье США.

К 22 октября 11:12 UTC все основные серверы баз данных снова находились на восточном побережье. Для ускорения репликации были добавлены дополнительные серверы-реплики. В 16:24 UTC после завершения синхронизации была восстановлена исходная топология.

Затем началась обработка накопившихся очередей веб-хуков и сборок GitHub Pages. После обнаружения удаления около 200 тысяч событий из-за истечения TTL обработка была приостановлена, а срок хранения сообщений увеличен. В 23:03 UTC все очереди были обработаны, корректность работы систем подтверждена, а статус GitHub изменён на зелёный.

**Последующие действия**

По результатам анализа инцидента GitHub определил следующие технические и организационные меры:

1. Изменение конфигурации Orchestrator: запретить автоматическое переключение основных серверов баз данных между регионами.
2. Улучшение мониторинга и информирования: внедрить новую систему статусов, отображающую состояние отдельных компонентов платформы, а не только общий статус сервиса.
3. Повышение отказоустойчивости инфраструктуры: ускорить переход к архитектуре active/active/active с обслуживанием трафика из нескольких центров обработки данных.
4. Устранение несогласованности данных: проанализировать бинарные журналы MySQL, определить операции записи, требующие автоматической или ручной сверки с пользователями.
5. Улучшение коммуникации: повысить точность прогнозов времени восстановления и информирования пользователей во время инцидентов.
6. Развитие практик тестирования отказов: внедрить систематическую проверку сценариев отказа, включая fault injection и chaos engineering.
Основная цель последующих изменений — исключить повторение подобных инцидентов, повысить отказоустойчивость инфраструктуры и обеспечить сохранность и согласованность пользовательских данных.

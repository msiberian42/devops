## Домашнее задание к занятию "13.Системы мониторинга"

### Обязательные задания

**1. Вас пригласили настроить мониторинг на проект. На онбординге вам рассказали, что проект представляет из себя платформу для вычислений с выдачей текстовых отчетов, которые сохраняются на диск. Взаимодействие с платформой осуществляется по протоколу http. Также вам отметили, что вычисления загружают ЦПУ. Какой минимальный набор метрик вы выведите в мониторинг и почему?**

HTTP-метрики: количество запросов в секунду (RPS) (показывает интенсивность нагрузки), доля ошибок HTTP (4xx/5xx) (позволяет обнаружить проблемы с обработкой запросов), время ответа (показывает, насколько быстро сервис отвечает пользователям).

Метрики вычислений: количество активных вычислений (показывает текущую параллельную нагрузку), время выполнения вычислений (помогает понять, не замедлились ли вычисления при росте нагрузки или нехватке ресурсов), количество завершившихся с ошибкой вычислений.

Метрики CPU: загрузка CPU (%), CPU usage процесса приложения (позволяет понять, какую долю ресурсов процессора потребляет непосредственно сервис).

Метрики диска: свободное место на файловой системе (%) и в байтах, количество свободных inode (в линукс при отсутствии свободных inode невозможно будет записать файл даже при наличии места на диске), задержку операций чтения и записи, ошибки записи отчётов.

**2. Менеджер продукта посмотрев на ваши метрики сказал, что ему непонятно что такое RAM/inodes/CPUla. Также он сказал, что хочет понимать, насколько мы выполняем свои обязанности перед клиентами и какое качество обслуживания. Что вы можете ему предложить?**

Можно разделить мониторинг на два уровня: технический для команды разработки и бизнес-метрики для ПМ и заказчика, а такэе ввести SLO, SLA, SLI для измерения качества обслуживания.

Технические метрики:
RAM	- сколько оперативной памяти использует платформа и хватает ли ей ресурсов для работы.
Inodes	- сколько файлов может ещё хранить файловая система; их нехватка может помешать сохранению отчётов даже при наличии свободного места
CPU Load Average (CPU LA) -	насколько процессор и система перегружены задачами, ожидающими выполнения

Измерение качества обслуживания:
SLI (Service Level Indicator) — измеримый показатель качества сервиса.
SLO (Service Level Objective) — целевое значение показателя, которого стремится достичь команда.
SLA (Service Level Agreement) — обязательство перед клиентом, часто закреплённое в договоре и предусматривающее последствия нарушения.

Бизнес-метрики:
Доступность сервиса - например, 99% успешных запросов в месяц.
Успешность вычислений - 90% вычислений завершаются корректно
Время выполнения - 90% вычислений завершаются в установленный лимит времени
Успешность сохранения отчетов - 99% отчетов успешно сохраняются

**3. Вашей DevOps команде в этом году не выделили финансирование на построение системы сбора логов. Разработчики в свою очередь хотят видеть все ошибки, которые выдают их приложения. Какое решение вы можете предпринять в этой ситуации, чтобы разработчики получали ошибки приложения?**

Если приложения работают в Docker или Kubernetes, можно договориться с разработчиками чтобы ошибка выводились в stderr. Тогда они будут доступны через docker logs.
Также можно развернуть одну из бесплатных систем мониторинга: Grafana Alloy, Fluent Bit, OpenSearch.

**4. Вы, как опытный SRE, сделали мониторинг, куда вывели отображения выполнения SLA=99% по http кодам ответов. Вычисляете этот параметр по следующей формуле: summ_2xx_requests/summ_all_requests. Данный параметр не поднимается выше 70%, но при этом в вашей системе нет кодов ответа 5xx и 4xx. Где у вас ошибка?**

Скорее всего, ошибка в формуле расчёта SLA: в знаменатель summ_all_requests попадают не только ответы 2xx, 4xx и 5xx, но и другие HTTP-коды, например 3xx (редиректы). Если 4xx и 5xx отсутствуют, но доля 2xx составляет только 70%, то оставшиеся 30% могут приходиться на 3xx, например 301, 302 или 304.

**5. Опишите основные плюсы и минусы pull и push систем мониторинга.**

Pull-модель — система мониторинга сама забирает метрики у наблюдаемых сервисов.

Push-модель — сами сервисы или агенты отправляют метрики в систему мониторинга.

Преимущества Pull-модели: централизованный контроль интервала сбора и таймаутов; удобно проверять доступность каждого источника; можно обнаружить, что метрики перестали поступать из-за отказа сервиса или сетевой проблемы; хорошо подходит для постоянных сервисов и инфраструктурных метрик.

Недостатки Pull-модели: требуется обнаружение новых экземпляров сервисов и управление конфигурацией опроса; краткоживущий процесс может завершиться до очередного опроса.

Преимущества Push-модели: подходит для короткоживущих задач, которые могут завершиться до следующего опроса; источник может отправлять данные сразу после события или по заданному интервалу; подходит для передачи метрик через промежуточные шлюзы и агенты.

Недостатки Push-модели: сложнее понять, почему данные перестали поступать: из-за отсутствия нагрузки, сбоя отправителя или проблем с сетью; кужно контролировать доставку, буферизацию, повторы и потери данных.

**6. Какие из ниже перечисленных систем относятся к push модели, а какие к pull? А может есть гибридные?**

Prometheus - основная pull (опрашивает метрики у target), для краткоживущих задач поддерживает Pushgateway, откуда затем сам забирает метрики.

TICK - гибридная, поддерживает input-плагины для сбора данных по Pull и output-плагины для отправки данных по Push в InfluxDB.

Zabbix - гибридная, поддерживает пассивные проверки, когда Zabbix server опрашивает агента, и активные проверки, когда агент сам отправляет данные серверу.

VictoriaMetrics - гибридная, поддерживает Pull через vmagent и Push через Prometheus.

Nagios - гибридная, Обычно Nagios инициирует проверки хостов и сервисов (Pull), но результаты проверок могут передаваться извне через механизм Passive Checks (Push).
